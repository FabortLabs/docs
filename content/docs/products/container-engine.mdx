Container Engine runs a containerized application as a versioned service inside a project.

## Create a service

Open **Container Engine**, select **New Container Service**, and choose a source:

- **Git Provider** connects a personal GitHub, GitLab, or Bitbucket Cloud account and selects one of its repositories. Providers that have not been configured by the platform remain visible but disabled.
- **Git Repository** verifies the repository before creation, fetches its branches, selects its default branch, and detects common runtime, Dockerfile, command, and exposed-port settings. Public repositories need no credential. For private repositories, select or create an encrypted Git HTTPS/SSH project credential and verify again.
- **Existing Image** deploys a public OCI image directly or uses an OCI registry credential store for a private registry.

Source deployments run as isolated BuildKit jobs. Fabort records the resolved build operation, pushes an immutable image, and creates the workload only after the build succeeds. Failed builds do not change active traffic and can be retried manually.

Configure the service name, region and availability zone, exposed ports and protocols, minimum and maximum replicas, CPU target, and a machine preset or machine template. Optional settings include persistent disks, entrypoint, typed environment variables, secret-backed environment variables, readiness and liveness paths, Docker context, Dockerfile path, build command, and run command.

Repository verification rejects embedded credentials, inaccessible branches, unverified SSH hosts, and repository hosts that resolve to local, private, link-local, or metadata networks. Changing the repository or credential invalidates the previous verification. Creation verifies the selected branch again before a build starts.

Git HTTPS credentials contain a username and token. Git SSH credentials contain a private key and a verified `known_hosts` entry. Fabort never obtains and trusts a self-hosted SSH key automatically; verify its fingerprint through a trusted channel first.

## Platform configuration

Source builds require `CONTAINER_BUILD_REGISTRY_PUSH_PREFIX`, `CONTAINER_BUILD_REGISTRY_PULL_PREFIX`, `CONTAINER_BUILD_IMAGE_PULL_SECRET`, and a build-worker image selected with `CONTAINER_BUILD_JOB_IMAGE`. The supplied `fabort-build-worker:prod` image is used by default.

Git provider connections use a shared callback in `GIT_OAUTH_CALLBACK_URL` and the provider credentials `GITHUB_CLIENT_ID`/`GITHUB_CLIENT_SECRET`, `GITLAB_CLIENT_ID`/`GITLAB_CLIENT_SECRET`, and `BITBUCKET_CLIENT_ID`/`BITBUCKET_CLIENT_SECRET`. A provider is disabled unless its client ID, client secret, and the callback URL are all present.

For preset machines, persistent disks are mounted under `/mnt/disks/<disk-name>`. A machine template supplies its own disk configuration.

Services replace their single active deployment immediately and retain up to 100 revision snapshots, including the active revision. Older revisions do not run. Warm versions, deferred promotion, traffic splitting, and automatic rollback are unavailable; the wizard disables unsupported release choices. Persistent disks use ReadWriteOnce storage. Both APIs enforce at most one replica on create, update, scale, and start; a stopped service may have zero desired replicas.

The Studio Machine step shows current organization and project reservations, remaining CPU and memory, and the proposed service reservation. Reservations include containers, games, and databases in every project and use each running workload's maximum replica count. Stopped workloads reserve no CPU or memory. The backend checks quotas again when a change is submitted.

New disks default to 1 GiB and are checked against the current plan. Existing volumes above a lowered plan limit remain editable without expansion; new disks and increases still require quota. The same growth-only checks apply to workload replica, volume-count, and environment-count limits.

## Operate a service

The **Overview** shows service status, ready and desired replicas, the active version, endpoint, current configuration, and recent deployments. Start, stop, kill, and restart require execute permission and act on the active version. A request for an older revision is rejected so a stale page cannot stop a newer rollout.

The remaining service pages provide:

- **Scaling** — set replica bounds, CPU and optional memory targets, scale-up policy, and a 1, 5, or 10 minute scale-down delay. It also reports current HPA state.
- **Network** — create, edit, and remove HTTP, HTTPS, TLS, TCP, and UDP endpoints with internal or public exposure. The endpoint name is the default hostname label, and the complete hostname and availability state appear below the name while you type.
- **Files** — choose a running pod, browse directories, read and write files, create directories, and delete paths.
- **Logs** — stream container logs, inspect pod issues and Kubernetes events, and copy visible log lines.
- **Metrics** — view live CPU, memory, network, disk, IOPS, replica, pod, and event data.
- **Audit** — review events scoped to this service.
- **Settings** — update the display name, image, environment, health checks, and shutdown grace period. Image or runtime configuration changes create a new revision and deployment-history entry. The first successful source build fills the initial revision; later rebuilds create new revisions. An apply failure remains visible in that history; retrying the same change reuses the pending revision.

<Callout type="warn" title="Runtime file changes are pod-local">
  The file browser operates on a selected running pod. Treat image or deployment
  configuration as the durable source of truth unless the edited path is backed
  by persistent storage.
</Callout>

Endpoint names are immutable after creation. To rename one, delete it and
create a replacement. Public HTTP, HTTPS, and TLS hostname labels can be edited and are verified before
the mutation is enabled. A response may be pending while the network controller
applies the change. The previous hostname stays reserved until the new route is
ready; failed changes remain observable and are retried by the controller.
