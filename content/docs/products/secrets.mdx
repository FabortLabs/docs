title: Secrets
description: Type, version, rotate, and consume sensitive project variables.

---

Secrets group related encrypted environment variables inside a project. A group is versioned as one bundle, so consumers never observe a mixture of keys from different updates.

## Create variables

Open **Secrets** and select **Create Secret**. Supply a name, optional metadata, and one or more typed variables. Credential templates such as Git HTTPS, Git SSH, and OCI registry are not secret types.

- **String** for text, URLs, tokens, and multiline values.
- **Integer** for whole numbers.
- **Float** for finite decimal values.
- **Boolean** for `true`, `false`, `1`, or `0`.
- **JSON** for valid JSON objects, arrays, or scalar values.

Type validation happens in both the frontend and backend. Like dotenvx and process environments, every value is ultimately injected into a workload as a string; typing validates authoring intent and is retained as metadata.

Values are not returned in list responses.

## Reveal and update

Open a secret to reveal its current bundle. Reveal is an audited operation and requires secret-value read permission. List and metadata responses expose key names and non-sensitive variable types, never values.

Saving replaces the complete bundle and creates an immutable version. A change note is optional. Consumers pinned to the latest version are refreshed by the backend.

## Version history and rollback

Version history identifies create, update, rotate, and rollback events. Rolling back does not overwrite history: it saves the selected old value as a new current version.

## Delete

Deleting a store permanently removes every bundle version. Remove service and database references first; the confirmation dialog requires the store name.

<Callout type="warn" title="Breaking migration">
  The secret-store schema replaces the former flat secret schema. The migration intentionally removes legacy secret values and audit rows; recreate required stores before redeploying dependent workloads.
</Callout>

<Callout type="warn" title="Rotation schedules are metadata in the frontend">
  You can set a rotation interval and see the next rotation timestamp, but the frontend does not expose a scheduler status page or rotation-job history. Verify automated-rotation behavior in the deployment where it is enabled.
</Callout>
