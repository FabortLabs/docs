Secrets hold a project's environment variables, encrypted at rest. A **store** (for example `api`) has one **config** per **environment** (`development`, `staging`, `production`, or your own), and each config is versioned as one bundle, so consumers never see a mixture of keys from different saves.

## Stores, environments, and configs

Open **Secrets** to see every store against every environment. Select **Add** in an empty cell to create that environment's config, or **New store** to start a store.

- **Branch configs** (for example `preview-42`) inherit their environment's config and override keys. Workloads may use them.
- **Personal configs** belong to one user. Only that user can see or change one, nobody can be granted access to it, and resources cannot use it. It inherits the environment's config, which makes it the place to override keys for a local `.env`. Personal configs never need a change request.
- **Inheritance**: a config may extend up to five other configs of the project; its own keys win.

Each variable has a type: string, integer, float, boolean, or JSON. Typing is validated in Studio and Bark and kept as metadata; every value reaches a workload as a string.

## References

Values can include other values, resolved whenever a consumer reads the config:

- `${KEY}` is a key of the same config.
- `${env.KEY}` is a key of the same store in environment `env`.
- `${store.env.KEY}` is a key of another store.
- `$${` is a literal `${`.

Saving a reference or inheritance requires read access to the configs it names, and cycles are refused. A workload pinned to an old version pins only that config's own values: inherited and referenced values always follow their latest version.

## Key visibility and notes

Each key is **masked** (revealed on demand), **unmasked** (shown without a click), or **restricted** (write-only). Restricted values still reach workloads, databases, and GitHub syncs, but never a reveal, export, share, or webhook. Making a restricted key visible again needs a new value in the same save. Keys can carry a note, and the config page shows when each key last changed and was last used.

## Reveal, import, and export

Revealing values is audited and requires secret-value read permission. List and metadata responses carry key names and types, never values.

**Import** accepts `.env`, JSON, or YAML. It merges, or replaces the config's keys, and shows the added, changed, and removed keys before you confirm. **Export** downloads `.env`, JSON, or YAML of the computed or stored values; it needs secret-value export permission, is audited, and leaves restricted keys out.

## Versions, snapshots, and rollback

Every save creates an immutable version, with an optional change note. Rolling back saves the selected old values as a new current version rather than rewriting history. Workloads that follow the latest version are re-applied on every change, including changes to configs they inherit or reference. The **Used by** section lists them, with a manual redeploy.

**Snapshots** record every config version in an environment at once. Restoring a snapshot first takes a safety snapshot, then rolls each config back to its recorded version.

## Protected environments

An environment can be marked protected with a number of required approvals. Edits, imports, rollbacks, restores, and deletes of its configs become **change requests**. Someone other than the author approves a request, and applying it fails if any config changed since the request was written. Administrator edits made from Operator are audited overrides and bypass change requests.

## Rotation

Choose keys to generate, with a length and character set, and an optional interval in days. A scheduled rotation writes newly generated values as a new version. A failed rotation keeps the schedule, records the error, and retries. Rotating by hand uses the same generators.

## Share links

**Share links** carry a value, or a config's visible keys, to someone outside the project. The link expires and allows a fixed number of views. Text is encrypted in your browser. A config share is encrypted by Bark with a key it returns once and never stores. Either way the key travels only in the link's `#fragment`. Opening a link counts as a view only after a deliberate click, so link previews do not use it up.

## Webhooks and audit export

Webhooks POST a JSON description of secret events to an HTTPS endpoint on a public address. Bodies never carry values. Each request is signed with `Fabort-Signature: t=<unix>,v1=<hex HMAC-SHA256 of "t.body">` using the webhook's signing secret, which is shown once. Failed deliveries are retried with backoff, and recent attempts are listed per webhook. Subscribing to read or export events streams the audit log, so it needs audit export permission.

The **Audit log** page lists a project's secret events for a time range and downloads them as CSV, an action that is itself audited.

## GitHub Actions sync

A config can push its computed values to GitHub Actions secrets of a repository, or of one of the repository's deployment environments. The push uses the GitHub connection of the person who created the sync, who needs admin access to the repository and secret-value export permission in Fabort.

- Values are encrypted with the repository's public key before they leave Bark.
- A push runs after every change to the config, or to a config it inherits or references, and on demand with **Sync now**. Failures are retried with backoff, and the last error is shown on the config.
- GitHub stores secret names in upper case and allows only letters, digits, and `_`, with no leading digit or `GITHUB_` prefix. A config with other key names fails to sync until they are renamed.
- Keys removed from the config are deleted from GitHub on the next push. Stopping a sync leaves the GitHub secrets in place.
- If the creator can no longer read the config, pushes stop with an error, and someone with access must recreate the sync.

## Limits

Plans limit the number of configs, environments, webhooks, active share links, and GitHub syncs. See **Usage** for your organization's limits.

## Delete

Deleting a config permanently removes every version and its GitHub syncs. Remove workload and database references, and the configs that inherit from or reference it, first.
