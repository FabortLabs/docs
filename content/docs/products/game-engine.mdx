Game Engine runs one stateful dedicated-server instance from a platform-managed game version. Games, versions, images, installers, lifecycle commands, files, ports, variables, resources, and storage are stored in named database fields instead of opaque catalog JSON.

## Create a game server

1. Open **Game Engine** and select **Launch Game Server**.
2. Enter a server name, select a game and version, then choose one of the version's administrator-approved runtime images.
3. Complete the version's typed settings. Secret settings reference project secret keys and are never entered as plaintext.
4. Choose a platform machine preset or a reusable project machine template. Its CPU and memory must fit the version's administrator-defined safety envelope. A template disk whose name matches a catalog volume supplies that volume's size.
5. Review the version's prefilled network endpoints. You can add, remove, or change endpoints before creation.
6. Select a region and availability zone, then create the server.

Images, digests, installation scripts, startup and stop commands, managed files, and storage mount paths are controlled by the selected version. Network endpoints start from version defaults and remain independently editable. Tenants cannot substitute arbitrary images or commands. A version can use a prebuilt image, SteamCMD, or a digest-pinned installer image and bounded installation script. Installers run against persistent storage before the game starts.

Catalog network definitions are editable presets for the same unified networking system used by other workloads. Target ports are container-local and may safely use the same number in every tenant workload. The endpoint name is the default hostname label, and the complete hostname and availability state appear below the name while you type. HTTP and HTTPS use hostname gateway routing, TLS passes encrypted traffic through to the workload, and public TCP/UDP/TLS endpoints receive an address and port from the selected cluster's configured pool through an atomic allocation claim. Users may override the default hostname or request a public address or port; blank allocation fields request automatic assignment. Tenants never share the same public hostname or public IP, port, and protocol tuple, and creation fails cleanly when no compatible route or allocation pool is available.

Fresh installations seed Minecraft Vanilla and Minecraft Paper versions. Administrators manage these and additional games under Operator's **Catalog Management → Game Engine**.

## Operate a server

- **Overview** reports runtime status, endpoint, release, configuration, health, events, and supports restart.
- **Console** opens a streaming game console for the selected running pod and accepts commands.
- **Files** provides pod file browsing, reading, writing, directory creation, and deletion.
- **Metrics** charts CPU, memory, network, disk, IOPS, replicas, pods, and events.
- **Network** creates, edits, and removes HTTP, HTTPS, TLS, TCP, and UDP endpoints with internal or public exposure.
- **Worlds** lists configured persistent volumes and mount paths.
- **Backups** creates private, crash-consistent RustFS archives, verifies SHA-256 checksums, offers short-lived downloads, and restores verified archives while the server is stopped. Running servers receive a daily backup and retain the newest seven completed archives. Stop the server first when an application-consistent archive is required.
- **Versions** performs an explicit upgrade to another catalog version and approved image while the server is stopped. Persistent volumes are retained; a failed Kubernetes apply attempts to restore the previous workload definition.
- **Reinstall** re-runs the selected version's installer while retaining persistent data. The server must be stopped before reinstalling.
- **Audit** shows events scoped to the game service.

Game servers are intentionally single-instance workloads backed by a StatefulSet, headless Service, and platform-managed persistent volume claims. The list page can permanently delete a game server workload; create a backup before deleting data you need to retain.

## Platform catalog lifecycle

Administrators use separate list, create, detail, and edit pages in Operator. The game detail page contains the version table, and versions have their own create and edit pages. Each version names its install strategy, one or more digest-pinned runtime images, installer image and script, process lifecycle, readiness check, resource envelope, typed tenant variables, default network endpoints, optional persistent volumes, backup eligibility, file templates, and structured file patches. Nothing in this contract is Minecraft-specific; Minecraft Vanilla and Paper are ordinary seeded entries using the same fields as any SteamCMD, prebuilt-image, or scripted dedicated server.

File templates are created only when the target file does not already exist. Structured patches are enforced during startup. All managed file paths must live inside a declared persistent-volume mount.

Runtime images are part of the platform contract: they must provide `/bin/sh` for lifecycle and configuration setup, plus `tar` and the standard file utilities used by backup and restore helpers. The platform runner owns the process input channel, so the configured stop command is sent to the game process during graceful termination.

Saving validates the complete version and makes it tenant-visible immediately. Existing services remain pinned to their stored runtime contract until an explicit version upgrade or reinstall. Legacy generic catalog tables and JSON templates are deleted rather than migrated.

## Incomplete pages

The following pages are present but are not complete management features:

- **Players** only reports node count and states that player sessions require a future game adapter/RCON integration.
- **Worlds** is currently read-only; it lists volumes but does not manage worlds as game-level objects.
